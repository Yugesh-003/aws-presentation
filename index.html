What Is a Server?

A server is a computer that provides services or resources to other computers.

🍽️ Restaurant Analogy
Customer = You (the user making a request)
Waiter = Your request traveling over the internet
Kitchen = The server processing your request
Food = The response (webpage, file, data)
  • A server is just a computer configured to serve others
  • It doesn't need to look special — it's the role that matters
  • Servers run 24/7 to be available when needed
  • A server can serve websites, files, databases, emails, and more
Personal Computer

Used by one person to run applications, browse the web, write documents. Not typically set up to serve others.

vs.
Server

Set up to respond to requests from many other computers. Often kept in data centers. Can be any computer with the right software configuration.

What Is On-Premises Infrastructure?

When an organization owns and manages its own servers at its own location.

Organizations traditionally purchased physical servers and managed all their own infrastructure. This meant:

Software-created computer that runs inside another computer.

A virtual machine (VM) is a software-created computer that runs its own operating system and applications — using resources provided by a physical host machine.

Protecting Your EC2 Instance

Security groups act as virtual firewalls controlling allowed network traffic.

House analogy:
🏠 EC2 Instance = your house
🚪 Security Group = rules about who can knock on which door
🔑 SSH/RDP = keys for authorized admins to enter
🌐 Internet = the neighborhood outside
  • Security Groups — virtual firewall rules for inbound and outbound traffic
  • Inbound rules — what traffic is allowed TO reach your instance
  • Outbound rules — what traffic your instance can send OUT
  • SSH (port 22) — Linux remote admin (restrict to trusted IPs only)
  • RDP (port 3389) — Windows remote admin (restrict to trusted IPs)
  • HTTP/HTTPS — web traffic, typically open to internet
⚠️ Security Best Practice

Never open all ports to the internet (0.0.0.0/0) for SSH or RDP. Allow administrative access only from specific trusted IP addresses. Follow the principle of least privilege.

Vertical Scaling

Make your existing server more powerful. Also called "scaling up".

Vertical scaling = taking your existing server and giving it more resources: more CPU, more RAM, more storage.
  • Pros: Simple — same server, same setup, no code changes
  • Pros: Good for many single-instance workloads
  • Cons: Physical limits — you can only make one server so big
  • Cons: May require a restart or brief interruption to change instance type
  • Cons: Single point of failure remains
Analogy: Like upgrading your laptop from 8 GB RAM to 32 GB RAM. Same machine, more power.

Horizontal Scaling

Add more servers to distribute the work. Also called "scaling out".

Horizontal scaling = adding more servers and distributing traffic across all of them using a load balancer.
  • Pros: Can handle much higher aggregate traffic
  • Pros: If one server fails, others keep serving traffic
  • Pros: Scale up and down dynamically
  • Cons: Requires suitable application architecture
  • Cons: Shared data and sessions need careful design
  • Cons: More infrastructure to manage
Analogy: Instead of one very fast cashier, open more checkout lanes. Each handles some customers — together they serve everyone faster.

Why We Need S3 Versioning

Accidentally overwrote your file? Versioning lets you recover it.

Scenario: A student uploads project.docx, edits it several times. Accidentally uploads a corrupted version. Without versioning — the original is gone forever.
  • Version ID — unique identifier for each saved version
  • Current version — the latest upload (what users see by default)
  • Previous versions — preserved when versioning is enabled
  • Delete marker — a special "tombstone" when an object is deleted in a versioned bucket
Enable Versioning

Enable on the bucket's Properties tab in the AWS Console. Note: keeping many versions increases storage costs. Versioning alone is not a substitute for a complete backup strategy.

Section G · Slide 31 of 38

What Is S3 Glacier?

Archive storage for data you rarely need but must keep.

Office analogy:
📋 Standard storage = files on your desk (instant access)
🗂️ Standard-IA = files in a nearby drawer (a moment to retrieve)
🏛️ Glacier = files in a long-term archive room (planned retrieval)
These are analogies. Actual retrieval times depend on which Glacier storage class and retrieval option you choose.
  • Old project submissions kept for compliance
  • Historical financial reports (7+ years)
  • Medical imaging archives
  • Research datasets rarely accessed
  • Legal records with long retention requirements
Important Clarification

Glacier is not a separate physical device you manage. It's a set of S3 storage class options — you select the storage class when uploading objects or via lifecycle policies.

Glacier Instant Retrieval

Retrieval: milliseconds. Good for archives accessed once a quarter. Same latency as S3 Standard when retrieved.

Glacier Flexible Retrieval

Retrieval: minutes to hours (Expedited ~1-5 min, Standard ~3-5 hrs, Bulk ~5-12 hrs). Very low storage cost. Plan your retrieval in advance.

Glacier Deep Archive

Retrieval: typically 12 hours (Standard) or 48 hours (Bulk). Lowest S3 storage cost. For data accessed once or twice per year at most.

Hands-On Troubleshooting

❌ Bucket name already taken
S3 bucket names are globally unique across all AWS accounts. Add a unique suffix (e.g., your initials + date: intro-cloud-demo-ab-20240301). Avoid generic names.
❌ "Access Denied" or insufficient permissions
Your IAM user or role may not have the required S3 permissions. Ask your instructor or account administrator to grant S3 access (e.g., AmazonS3FullAccess policy for this exercise). Never share root credentials.
❌ Wrong AWS Region
Check the region selector in the top-right corner of the AWS Console. Switch to your intended region and look for your bucket there. Buckets are region-specific.
❌ Upload fails or times out
Check your internet connection. Try a smaller file (a plain .txt file works well). Ensure you have S3:PutObject permission. Refresh the page and try again.
❌ Versioning toggle not visible
Go to the bucket → Properties tab → scroll down to "Bucket Versioning" section. If it's still not visible, check that you have the bucket open (not the S3 homepage) and have sufficient permissions.
❌ Can't access object via URL
This is expected — the bucket is private by default. Use the "Download" button in the console, not the object URL directly. The URL requires AWS authentication, which the browser alone cannot provide.
❌ Unexpected charges concern
Delete the bucket and all objects after the demonstration. Check your billing dashboard. For small test files, charges are typically negligible, but always clean up. Use the AWS Free Tier if eligible.
